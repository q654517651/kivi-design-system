# 验收

主要给 UI 设计师用：开发做完后，对照 Figma、规范、需求，查开发稿能不能上线。也用来审查单独的设计稿或代码是否合规。

规范的数值只在网站（`site/`）。这里只写怎么验、查什么、怎么出报告。

## 1. 先收材料

| 材料 | 必备吗 | 用来查 |
|---|---|---|
| Figma 设计稿（链接到具体页面或节点） | 必备 | 样子、尺寸、状态图、文案 |
| 前端代码（仓库、分支或 MR） | 必备 | 变量、组件用法、写死的值、状态写没写 |
| 能运行的页面（测试环境地址或本地） | 必备 | 交互、动效、滚动、状态切换 |
| 需求文档 | 可选 | 功能、文案、边界情况 |
| 参考项目或线上产品 | 可选 | 交互照谁做 |

- 有参考项目，或者 Figma 状态图画得完整（空、加载、失败、多与少都有），就可以不要需求文档。
- 缺必备材料，先跟用户要。要不到就照常验，缺的部分在报告里写「未检查」，不要猜。
- 不同材料能查到哪一步：

| 只拿到 | 能查 | 不能下结论 |
|---|---|---|
| 源码 | 变量、写死的值、组件用法、状态写没写 | 视觉、布局 |
| 截图或设计稿 | 颜色、字号、间距、圆角、层级、布局 | 悬停、键盘、动效、状态切换 |
| 能运行的页面 | 上面都能查，再加交互、滚动、动效 | — |

## 2. 定范围

动手前先列出要验的页面和状态，和用户对一下：

- 页面：这次改了哪些页、哪些弹窗和浮层。
- 状态：每页要验哪些状态，照下面第 3 步「状态」那一节挑。
- 窗口：最小宽、常用宽（1440）、宽屏；浏览器缩放 100% 和 125%。

## 3. 逐项查

按页面一页一页过。每页先跟 Figma 并排对一遍样子，再在能运行的页面上把状态和交互点一遍，最后看代码。

### Figma 和开发是否一致

- 布局：位置、对齐、宽高、间距。
- 文字：字号、字重、行高、颜色、截断方式。
- 颜色和底色层级、描边、圆角、透明度。
- 图标：名字和图形都对，大小对。
- 文案：一字不差；同一件事全站用同一个说法（比如失败统一「生成失败，消耗猕猴桃已退回」）。
- 图片和视频：比例、裁切方式（铺满裁切还是留边）、加载前有没有占位。

### 变量和组件（两边都查）

开发稿：
- 颜色、间距、圆角、字号、行高、透明度、时长、缓动都用 `tokens.css` 的变量，没有写死（布局宽度除外）。
- 用的是组件库里的组件，尺寸、类型、状态在网站参数表里有；没有为这一页另造按钮、菜单、弹窗。
- 没有直接用别的 UI 库的样子（比如 antd 默认的 message、Modal、Popover），要换成组件库里对应的组件。
- 没用旧名：旧变量名、旧组件名、旧图标名，查网站「旧名对照」给出新名。

Figma 稿：
- 用的是已发布的「KIVI UI KIT V2」库组件实例，没有拆散、没有仿画。
- 颜色、间距、圆角、字号都绑了变量或文字样式。
- 用户作品的位置是 PlaceholderImage 实例。

规范的硬规则（不符合就是「不一致」）：网站「设计规则」页 `site/src/docs/foundations/rules.mdx` 的每一条都过一遍，逐条对照，不在这里另写一份。

### 状态

每个模块都过一遍，Figma 没画、开发也没做的，记成「体验」问题。

- **内容多与少**：一个字和很长一段；一条和几十条；数字从 1 位变成 5 位；名字超长。长的是截断（几行、末尾怎么处理、能不能看全文）还是换行。
- **没有内容**：空状态用 `EmptyState`，有插图、标题、说明；能给下一步的放引导按钮（「去创作」「重试」）。
- **加载**：知道内容长什么样用骨架屏，不知道用转圈；生成中用点阵动效，不画进度条。
- **失败**：网络错误、生成失败、上传失败、无权限；失败后能重试，操作还在。
- **交互状态**：默认、悬停、按下、聚焦、选中、禁用、加载中。
- **滚动和超出**：列表超出能滚；滚动区域的渐隐跟着滑的方向；吸顶、吸底；浮层贴到窗口边会换方向，不被裁掉；窗口变窄时不挤坏、不出横向滚动条。
- **增加和删除**：加第一条、加到上限、删一条、删到空；删除要不要确认、有没有撤销；新加的出现在哪、列表会不会跳。
- **拖动**：拖动排序、拖到边上、拖出范围、松手后的落点。
- **输入**：必填为空、超长、非法字符、粘贴大段内容、上传超大或格式不对的文件。

### 交互

- 和需求或参考产品一致：点哪里出什么、什么时候出、什么时候收。
- 点外面、按 Esc 能关掉浮层和弹窗；关掉后焦点回到打开它的地方。
- 键盘能用：Tab 顺序合理，回车确认，方向键在菜单、选项卡、单选组里移动。
- 加载中、提交中按钮不能重复点。
- 悬停才出的东西（工具栏、删除按钮）不会一碰就闪。
- 同一时间只播一个视频或音频。

### 动效

- 该有的都有：出现、消失、展开收起、切换、拖动跟手、操作反馈（点了有反应）。
- 缓动和时长用变量：屏幕内移动 ease-in-out，出现 ease-out，消失 ease-in；只有循环动画（转圈、扫光）用匀速；不用 CSS 默认 `ease`。
- 时长合理：一般最长 400ms；成组展开 400 起每多一张 +10，最多 700。跟着动的东西和主体同时长。
- 不过度：不为了好看乱加弹跳、旋转；动效不挡操作。
- 系统开了「减少动态效果」时去掉位移和缩放，只留透明度或直接切换。
- 具体规则以网站「动效」页为准。

### 其他

- 可访问：只有图标的按钮有 `aria-label` 和 Tooltip；聚焦时看得见焦点框；文字在底色上看得清。
- 不跳：图片、字体加载前后布局不跳；切换状态时整体不抖。
- 控制台没有报错。

## 4. 分级和结论

| 级别 | 是什么 |
|---|---|
| 阻塞 | 功能用不了、数据错、页面崩 |
| 不一致 | 和 Figma 或规范硬规则不一样 |
| 体验 | 状态缺、交互不顺、动效缺或不合理 |
| 建议 | 能更好，但规范没要求（规范没覆盖的也放这里，标「规范未覆盖」） |

- 有「阻塞」或「不一致」：**不通过**。
- 只有「体验」「建议」：**通过，有遗留**，遗留问题列给前端排期。
- 都没有：**通过**。
- 不要把自己的审美偏好当规范。说不出依据在 Figma 哪个节点、网站哪一页，就不是「不一致」。

## 5. 每条问题怎么写

```
[阻塞 / 不一致 / 体验 / 建议] 页面 · 位置（文件:行，或截图里的区域）
现状：实际是什么（值、组件、表现）
应该：Figma 或规范里是什么
依据：Figma 节点链接，或网站哪一页哪一节（规范没覆盖就写「网站没有」）
改法：改成哪个变量、组件、属性，或者怎么改交互
截图：Figma 和开发并排
```

同一个原因导致的多处问题合成一条，列出所有位置。

## 6. 出报告

默认出一个单文件 HTML，截图嵌进去（base64），能直接发给前端。用户要别的格式（飞书文档、表格）就照用户的。

报告从上到下：

1. **结论**：通过 / 通过有遗留 / 不通过，各级问题各几条。
2. **范围**：拿到了哪些材料、验了哪些页面和状态、用的什么窗口宽度；没查的写「未检查」和原因。
3. **问题清单**：按 阻塞 → 不一致 → 体验 → 建议 排，每条照第 5 步写，带并排截图。
4. **按页面的状态表**：每页一行，每个状态一列，写「有 / 缺 / 未检查」。
5. **通过的项**：一句话带过，不逐条列。

截图：
- Figma：用 Figma 工具导出节点截图。
- 开发：在浏览器里打开页面，切到对应状态再截。
- 并排放，同一个比例，标出有问题的区域。

## 自查

报告发出去之前过一遍：

- 每条「不一致」都有依据链接。
- 没查的范围都写了「未检查」。
- 截图和文字说的是同一个状态。
- 改法写到前端能直接动手的程度：变量名、组件名、属性名。
